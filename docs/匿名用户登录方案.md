# 匿名用户登录方案

基于 [Supabase Anonymous Sign-Ins 文档](https://supabase.com/docs/guides/auth/auth-anonymous?queryGroups=language&language=python) 与当前项目架构（auth.meicity.net 鉴权 + Supabase 作数据库），给出可行方案与注意事项。

---

## 一、Supabase 文档要点与潜在问题

### 1.1 文档在说什么

- **signInAnonymously()**：在 **Supabase Auth** 里创建一个匿名用户，拿到带 `is_anonymous` 声明的 JWT，角色是 `authenticated`。
- **升级为正式用户**：通过 **linkIdentity**（OAuth）或 **updateUser**（email/phone + 验证）把匿名账号「绑定」成正式用户。
- **RLS**：用 `(auth.jwt()->>'is_anonymous')::boolean` 区分匿名与正式用户，配合 **restrictive** 策略使用。
- **风险与限制**：匿名用户会写入 `auth.users`，需防滥用（建议 CAPTCHA/Turnstile）、有 IP 限频（默认 30 次/小时）、无自动清理，需自行定时删旧匿名用户。

### 1.2 和你们现状的差异

| 项目 | 你们当前 | Supabase 文档假设 |
|------|----------|--------------------|
| 鉴权 | **auth.meicity.net**（微信静默登录 + 手机号/验证码），自建用户表 | **Supabase Auth**（JWT、auth.users） |
| 用户 ID 来源 | auth.meicity.net 返回的 `user.id` | Supabase Auth 的 `user.id` |
| 业务表 | cinema_order_list、user_member_cards、coupon_instance 等用 **自建 user_id**，Supabase 用 **anon key + body/query 传 user_id** | 通常用 Supabase JWT 的 sub 做 RLS |

也就是说：**你们没有用 Supabase Auth 做登录**，用户身份来自 auth.meicity.net，Supabase 只当数据库用。若直接照文档用 `signInAnonymously()`，会引入**第二套用户体系**（Supabase Auth 的 user id），和现有订单/会员卡/券的 `user_id` 不一致，需要大改表结构和调用方式。

---

## 二、推荐方案：在自建鉴权上做「匿名用户」（不接 Supabase Auth 匿名）

在 **auth.meicity.net** 侧增加「匿名用户」概念，不引入 Supabase Auth 的匿名登录，业务库和现有 `user_id` 不变。

### 2.1 流程简述

```
打开小程序
  → 微信静默登录（wx.login + code）
  → 调 auth.meicity.net：POST /auth/wechat-mp/login，Body { code }
  → 后端：若该 openid 尚无用户则创建「匿名用户」（is_anonymous=true，phone=null），若有则按现有逻辑
  → 返回 access_token + user（id, openid, is_anonymous: true, phone: null）
  → 前端：可浏览排期、选座、下单（若业务允许匿名下单）等，用同一 user.id 写订单/会员卡等

用户点击「微信手机号快捷登录」或「验证码登录」
  → 拿到手机号（getPhoneNumber 的 code 或验证码）
  → 调后端「绑定/升级」接口：把当前 user（匿名）与该手机号绑定，置 is_anonymous=false，phone=xxx
  → 返回更新后的 access_token + user
  → 前端：同一 user.id，后续订单/会员卡/券都仍用此 id，无需数据迁移
```

### 2.2 后端需要配合的内容（auth.meicity.net）

| 项 | 说明 |
|----|------|
| **wechat-mp/login** | 若 openid 无对应用户，可创建匿名用户：`is_anonymous=true`、`phone=null`，仍返回 `access_token`、`user`（含 `id`）。若已有用户则行为不变。 |
| **升级接口** | 提供「用当前 token + 手机号（或 getPhoneNumber 的 code）」将当前用户从匿名升级为正式：更新 `phone`、`is_anonymous=false`，返回新 token/user。可与现有「验证码登录/绑定」或「微信 getPhoneNumber 绑定」合并或复用。 |
| **权限** | 按需限制匿名用户能力（例如：可下单但不可用券、不可绑会员卡；或允许全部，仅差在「未绑手机」的提示）。 |

### 2.3 前端需要配合的内容（小程序）

| 项 | 说明 |
|----|------|
| **session 恢复** | 静默登录若返回 `user.is_anonymous === true`，仍写入 `supabaseUser`/`userinfo`，允许进入需要「已登录」的页；可在 UI 上提示「未绑定手机号，部分功能受限」或引导绑手机。 |
| **需手机号的能力** | 下单、会员卡、券等若要求「已绑手机」，判断 `!user.phone || user.is_anonymous` 时弹登录/绑手机（现有 phone-login-modal 或获取手机号按钮）。 |
| **升级后** | 绑定手机成功 → 后端返回新 user（同一 id、有 phone、is_anonymous=false）→ 前端更新 globalData 与本地存储，无需清空订单等数据。 |

### 2.4 数据与表

- **auth.meicity.net 用户表**：增加或使用字段 `is_anonymous`（或仅用 `phone 为空` 表示匿名），`phone` 绑定后更新。
- **Supabase 业务表**：**无需改**。订单、会员卡、券仍用同一 `user_id`（auth 返回的 `user.id`），匿名与正式用户是同一 id，只是从「匿名」升级为「已绑手机」。

### 2.5 优点与注意点

- **优点**：不引入第二套用户 id；不改 Supabase 表结构；升级时无需「匿名 user_id → 正式 user_id」的数据迁移或冲突处理；与现有购票/会员卡/券逻辑兼容。
- **注意**：匿名用户仍会占你们自建用户表一条记录，建议后端对「仅 openid、无手机」的创建做限频或简单风控（例如同一 openid 短时间内不重复创建匿名用户）。

## 三、备选方案：使用 Supabase Auth 原生匿名登录

若希望完全按 [Supabase 文档](https://supabase.com/docs/guides/auth/auth-anonymous?queryGroups=language&language=python) 用 **Supabase Auth** 的 `signInAnonymously()`，需要接受架构变化。

### 3.1 可行做法概览

1. **小程序内接入 Supabase Auth**（如使用支持小程序的 Supabase 客户端或自封请求）：
   - 启动时调用 `signInAnonymously()`，拿到 Supabase 的 session（JWT 含 `is_anonymous`）。
2. **业务表与 RLS**：
   - 订单、会员卡、券等表改为使用 **Supabase Auth 的 user id**（JWT 的 `sub`）作为 `user_id`。
   - RLS 用 `auth.uid()` 与 `auth.jwt()->>'is_anonymous'` 控制：例如仅允许非匿名用户写订单，或允许匿名用户写订单但限制其他表。
3. **与微信/手机号打通**：
   - Supabase 无微信 provider，需在「升级」时：用户通过你们后端完成微信 getPhoneNumber 或验证码 → 后端用 **Supabase Admin API** 对该匿名用户做 **updateUser**（绑定 phone）或通过 Custom JWT / 自定义逻辑把「微信用户」与 Supabase Auth 的 user 关联起来。文档中的 [Link an email/phone identity](https://supabase.com/docs/guides/auth/auth-anonymous?queryGroups=language&language=python#link-an-email--phone-identity) 需在你们后端用 Admin API 完成。

### 3.2 主要成本与问题

| 问题 | 说明 |
|------|------|
| **两套用户 id** | 当前订单/会员卡/券等用的是 auth.meicity.net 的 user_id；若改用 Supabase Auth，要么迁移历史数据到新 id，要么在很长一段时间内维护两套 id 的映射与兼容，复杂度高。 |
| **RLS 改造** | 目前是 anon key + 请求里传 `p_user_id` 等，若改为 Supabase Auth，需改为用 JWT 的 `sub`，并给所有相关表写 RLS（且注意文档中的 **restrictive** 与 `is_anonymous` 组合）。 |
| **微信/手机号绑定** | 需在后端实现：微信 code / 手机号 → 调 Supabase Admin API 做 updateUser 或 link，并处理好「匿名转正式」的冲突（文档 [Resolving identity conflicts](https://supabase.com/docs/guides/auth/auth-anonymous?queryGroups=language&language=python#resolving-identity-conflicts)）。 |
| **限频与清理** | 文档要求注意滥用与 [Rate limits](https://supabase.com/docs/guides/auth/auth-anonymous?queryGroups=language&language=python#abuse-prevention-and-rate-limits)（如 30 次/小时/IP）；匿名用户无自动清理，需 [自行定时删除](https://supabase.com/docs/guides/auth/auth-anonymous?queryGroups=language&language=python#automatic-cleanup) 旧匿名用户。 |

因此，在你们**已有一套成熟自建鉴权 + Supabase 仅作库**的前提下，更推荐采用**第二节「在自建鉴权上做匿名」**，避免大规模迁移和双 id 体系。

## 四、方案对比与建议

| 维度 | 方案一：自建鉴权匿名（推荐） | 方案二：Supabase Auth 匿名 |
|------|-----------------------------|----------------------------|
| 用户 id | 始终是 auth.meicity.net 的 user.id，与现有表一致 | 改为 Supabase Auth 的 user id，需迁移或双 id |
| 后端改动 | auth.meicity.net：支持匿名创建 + 升级接口 | 需 Supabase Auth + Admin API + 与微信/手机号的对接 |
| Supabase/表 | 无需改表、无需改 RLS | 需 RLS、可能需迁移数据 |
| 文档对应 | 不直接使用 Supabase 匿名文档，但「匿名 → 绑定升级」思路一致 | 完全按 Supabase 匿名文档实现 |
| 风险 | 需在自建侧做匿名限频与风控 | 需处理双 id、RLS、冲突与清理 |

**建议**：采用**方案一（自建鉴权匿名）**，在 auth.meicity.net 实现「匿名用户创建 + 手机号/微信获取手机号升级」，前端按「有 user 即算登录、按 phone/is_anonymous 控制功能」即可。若未来希望统一到 Supabase Auth，再单独规划迁移与 RLS 改造。

## 五、方案一实施清单（便于排期）

1. **后端（auth.meicity.net）**
   - [ ] wechat-mp/login：openid 无用户时创建匿名用户（is_anonymous=true, phone=null），返回 token + user。
   - [ ] 升级接口：当前 token + 手机号（或 getPhoneNumber code）→ 更新该用户 phone、is_anonymous=false，返回新 token/user。
   - [ ] （可选）匿名用户创建限频或简单风控。

2. **前端（小程序）**
   - [ ] 静默登录后若 user.is_anonymous 为 true，仍写入 supabaseUser，允许进入需登录页。
   - [ ] 需要手机号的操作前判断 user.phone / is_anonymous，无则弹登录/绑手机（沿用现有 modal 或获取手机号）。
   - [ ] 绑定/升级成功后用新 user 更新 globalData 与本地存储。

3. **Supabase**
   - [ ] 无需改表、无需改 RLS（继续用现有 anon + user_id 方式即可）。

4. **产品**
   - [ ] 明确哪些能力对匿名开放（如仅浏览、可下单等）、哪些必须绑手机后再用。
