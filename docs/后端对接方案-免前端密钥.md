# 后端对接方案：免前端持有 app_secret

## 一、问题

当前多端加签方案要求前端持有 `app_secret`（wechatAppSecret），用于对 `/api/v1/send-otp`、`/api/v1/verify-login` 等接口请求做 MD5 签名。  

**风险**：小程序代码可被反编译，`app_secret` 写在客户端存在泄露风险。

---

## 二、方案：以 WeChat 登录态替代 app_secret 签名

**核心思路**：微信小程序在调用发验证码、登录/注册接口前，必定已完成 **静默登录**，已持有有效的 `access_token`。后端可据此判断请求来自合法微信端，**无需前端再做 app_secret 签名**。

### 2.1 流程说明

| 步骤 | 前端 | 后端 |
|------|------|------|
| 1 | 静默登录获取 `access_token` | 校验 code，返回 token |
| 2 | 请求发验证码 / 登录时，Header 带 `Authorization: Bearer <access_token>` | 校验 token 有效 → 视为来自微信端 → 免验 X-Sign |

### 2.2 建议新增/调整的接口

在**保留**现有 `/api/v1/send-otp`、`/api/v1/verify-login`（供 App、抖音等需加签的端使用）的前提下，为微信小程序提供一套**免签**接口：

| 用途 | 方法 | URL（建议） | Header | Body |
|------|------|-------------|--------|------|
| 发送验证码 | POST | `/api/v1/send-otp-wechat` 或 `/auth/phone/send-otp` | `Content-Type: application/json`<br>`Authorization: Bearer <access_token>` | `{ "phone": "13800138000" }` |
| 验证码登录/注册 | POST | `/api/v1/verify-login-wechat` 或 `/auth/phone/login` | 同上 | `{ "phone": "13800138000", "code": "123456", "openid": "可选" }` |

### 2.3 后端校验逻辑

```
收到请求
  → 检查 Header 是否存在 Authorization: Bearer <token>
  → 校验 token 是否为当前微信静默登录签发的有效 token
  → 若有效：视为来自微信小程序，执行发验证码 / 登录逻辑，不校验 X-Sign
  → 若无效或缺失：返回 401
```

### 2.4 可选：复用旧接口

若后端已有且仍开放以下接口：

- `POST /auth/phone/send-otp`（无签）
- `POST /auth/phone/login`（无签）

可约定：当请求带有效 `Authorization: Bearer <wechat_token>` 时，**豁免**对 X-Sign 的校验，直接按现有逻辑处理。  
这样无需新增 URL，只需在验签逻辑中增加「有有效 WeChat token 则跳过签名校验」的分支。

---

## 三、前端后续改动

后端支持上述方案后，前端将：

1. 移除 `wechatAppSecret` 配置
2. 发验证码、登录请求统一使用 `Authorization: Bearer <access_token>`
3. 不再计算或传递 X-Sign、X-Sign-Time

---

## 四、小结

| 项目 | 说明 |
|------|------|
| 目标 | 前端不持有 `app_secret`，避免泄露 |
| 手段 | 用 WeChat 静默登录的 `access_token` 替代 app_secret 签名 |
| 后端改动 | 为微信端提供免签接口，或对带有效 token 的请求豁免签名校验 |
| 多端兼容 | 保留原加签接口供 App、抖音等端使用 |
