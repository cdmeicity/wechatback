# 退改签规则与前端接入说明

面向 **后端服务、小程序/App、对账脚本**：如何根据订单与当前时间解析 **哪条策略**、**哪条规则行**，以及如何计算手续费；以及 **微信小程序** 侧应如何传参、与现有代码对齐。表结构见 `refund_change_policy` / `refund_change_policy_rule`；产品级原则见 [退改签价格体系与规则引擎设计.md](./退改签价格体系与规则引擎设计.md)（若仓库内存在）。

**用户可见文案**仍以 [影院退改签协议.md](./影院退改签协议.md) 为准；本文偏 **技术实现与接口契约**。

---

## 1. 核心概念

| 概念 | 说明 |
|------|------|
| **策略** | `refund_change_policy` 一行；区分 `policy_type`：`refund`（退票）/ `change`（改签） |
| **规则行** | `refund_change_policy_rule` 多行；按 **距开场剩余小时数** 分段，每段一种计费方式 |
| **适用范围** | `scope`：`global`（全局）或 `store`（门店，对应 `department_id`） |
| **渠道（粗）** | `channel` 为空表示不按粗分渠道区分；非空为 `wechat_mp` / `douyin_mp` / `app`（见 §4） |
| **渠道（细，appid）** | `channel_appid` 为空表示不按具体应用区分；非空为 **`price_app_channel.appid`**（微信/抖音小程序 appid 或 App 固定值如 `app_meicheng`），与价格规则、应用渠道管理一致 |
| **生效时间** | `effective_from` / `effective_to` 为 **上海本地墙钟**、**无时区** `timestamp`；`effective_to` 为空表示长期有效 |

## 2. 解析顺序：先选策略，再选规则行

### 2.1 选一条策略（优先级从高到低）

在同时满足 **`status = 'active'`**、当前时刻落在 **`[effective_from, effective_to]`**（`effective_to` 为空则只判断 `>= effective_from`）、**租户**（见 §3）的前提下，用订单上的 **`department_id`（门店）**、**`channel_appid`（下单小程序/App 的 appid，与订单落库一致）**、以及粗粒度 **`channel`**（由 appid 映射或直接传入，见 §4）在候选策略中匹配。

**匹配顺序（数字越小越优先尝试；命中即停止）：**

| 顺序 | `scope` | `department_id` | `channel_appid` | `channel` |
|------|---------|-----------------|-----------------|-----------|
| 1 | `store` | = 订单门店 | = 订单 appid | 任意（建议配置为 NULL，避免歧义） |
| 2 | `store` | = 订单门店 | NULL | = 粗粒度渠道 |
| 3 | `store` | = 订单门店 | NULL | NULL（该门店下全渠道） |
| 4 | `global` | NULL | = 订单 appid | 任意 |
| 5 | `global` | NULL | NULL | = 粗粒度渠道 |
| 6 | `global` | NULL | NULL | NULL（全局兜底） |

**说明：**

- 订单侧应 **始终带 `appid`**（小程序启动参数、App 配置），解析策略时 **先按 `channel_appid` 精确命中**，再退回粗分 `channel`，最后全局兜底。
- 若某条策略同时写了 `channel_appid` 与 `channel`，以 **`channel_appid` 是否等于订单** 作为该行的主要语义；实现上仍按上表顺序筛选即可。
- 若同一档有多条，再比 **`priority`（越大越优先）**；仍相同则固定一种决胜规则（如 `id` 最大或 `effective_from` 最新）。

**未命中任何策略**：返回 `POLICY_NOT_FOUND` 等稳定错误码，并打监控。

### 2.2 在策略内选一条规则行

设 **`H`** = 从 **当前时刻** 到 **场次开场时间** 的剩余小时数（**正数**，已开场或过期则 `H ≤ 0`，由业务先判是否允许操作）。

对命中策略下的 `refund_change_policy_rule`，按 **`sort_order` 升序** 依次判断，找到 **第一条** 满足时间窗的行：

- 记 `min = time_before_departure_min_hours`，`max = time_before_departure_max_hours`
- **约定（与种子数据、后台配置一致）**：**左闭右开**  
  **`[min, max)`**  
  - `max IS NULL` 表示 **无上限**：`H ≥ min` 即命中  
  - 否则：`min ≤ H < max`

若多行互不重叠且覆盖全部 `H`，则至多命中一行；若有重叠，以 **先被遍历到的** `sort_order` 为准（配置时应避免重叠）。

### 2.3 计费方式 `fee_mode`（规则行）

| `fee_mode` | 含义 | `fee_value` 等 |
|------------|------|----------------|
| `percent_of_basis` | 按策略主表 **`fee_basis`** 对应金额 × 比例 | 小数，如 `0.2` = 20% |
| `fixed_amount` | 固定手续费 | **整数分**，如 `1000` = 10 元 |
| `percent_with_floor_ceiling` | 比例 + 保底/封顶 | 使用 `fee_floor_amount` / `fee_cap_amount`（分） |
| `no_refund` | 不可退票 | 不产生退票手续费，业务应拒绝退票 |
| `no_change` | 不可改签 | 不产生改签手续费，业务应拒绝改签 |
| `tiered_time` | 时间阶梯（扩展） | 由实现与配置约定 |

**`fee_basis`（策略主表）**：`ticket_face`（票面）/ `paid_amount`（实付）/ `sale_price`（售价），仅在与比例类模式一起使用时参与计算。

## 3. 租户 `tenant_id`

查询策略时建议：

```text
(tenant_id IS NULL OR tenant_id = :当前租户)
```

与现有后台列表、考勤等模块一致：**NULL 表示全租户通用**；若只使用单一租户，可全部写入固定 `tenant_id`。

---

## 4. 订单 appid 与粗粒度 `channel`

### 4.1 `channel_appid`（推荐主键）

- 与 **`price_app_channel.appid`**、**`price_rule.channel_appid`** 同一套数据：在「应用渠道管理」中维护每个微信/抖音小程序及 App 的 appid。
- 订单落库时应写入 **`appid`**（或可从支付/会话上下文唯一还原），退改签解析时 **优先用 `channel_appid = 订单.appid`** 命中策略。

### 4.2 粗粒度 `channel`（兜底）

当未配置 appid 级策略或订单无 appid 时，用粗分：

| 订单来源（示例） | 策略 `channel` |
|------------------|----------------|
| 微信小程序 | `wechat_mp` |
| 抖音小程序 | `douyin_mp` |
| 自有 App | `app` |

映射应在 **一处** 维护（常量或 `price_app_channel.channel_type` → 上述枚举）。

### 4.3 与 `order_channel` 字段的对应

业务里常见 `order_channel` = `miniprogram` / `douyin` / `app`，需映射到 **`channel`** 或直接从 **`price_app_channel`** 用 appid 反查，与 [票价RPC与渠道绑定说明.md](./票价RPC与渠道绑定说明.md)（若存在）保持一致。

## 5. 时间与 `H` 的计算

1. **开场时间**：使用订单/场次上的 **放映开始时间**（上海时区业务则统一按上海墙钟解析）。
2. **当前时间**：服务端建议用 **上海** `Asia/Shanghai` 与开场时间同一套日历，避免混用 UTC 与本地。
3. **`H`**：  
   `H = (开场时刻 - 当前时刻)` 转为 **小时**（小数允许，与规则里 `numeric` 一致）。

已开场（`H ≤ 0`）是否允许退改：由产品决定，**不在**本表强制；实现上可先短路并返回 `reason_code`（如 `REFUND_TOO_LATE`）。

## 6. 调用流程（建议）

```
输入：tenant_id、department_id（门店）、channel（映射后）、policy_type（refund|change）、
      场次开场时间、当前时间、订单金额字段（票面/实付/售价）、是否已改签次数等

1) 校验订单状态、资格（是否已取票、是否开场等）— 可与策略并行
2) 按 §2.1 查询并锁定一条 refund_change_policy
3) 计算 H，按 §2.2 在 refund_change_policy_rule 中取一行
4) 按 §2.3 计算手续费 / 是否禁止
5) 返回：是否允许、手续费明细、使用的 policy_id / rule_id（供快照）

下单或支付成功时：将 policy_id、version、规则摘要写入 order_refund_change_snapshot（或订单扩展字段）
```

小程序/App **不要** 各自实现一套公式；应调用 **同一服务端接口**（或 Supabase Edge Function），传入映射后的 `channel` 与 `department_id`。

## 7. 与全局种子数据对齐（示例）

脚本：`scripts/seed_refund_change_policy_global.sql`（策略名：`全局退票标准` / `全局改签标准`）。

在 **§2.2 左闭右开** 约定下：

- 退票：≥72h → 20%；[24, 72) → 50%；[0, 24) → `no_refund`
- 改签：≥72h → 0 元；[24, 72) → 1000 分；[2, 24) → 1500 分；[0, 2) → `no_change`

实现校验时可用上述边界点自测（如 `H = 72`、`H = 24`、`H = 2`）。

## 8. 数据库访问示例（只读查询形状，非最终 SQL）

伪逻辑（需在应用层拼参数、处理租户与时间）：

1. `SELECT * FROM refund_change_policy WHERE policy_type = $1 AND status = 'active' AND ... ORDER BY 匹配档位, priority DESC, effective_from DESC LIMIT 1`
2. `SELECT * FROM refund_change_policy_rule WHERE policy_id = $1 ORDER BY sort_order`

若用 **单条 SQL** 解析策略，可用 `CASE`/`OR` 嵌套表达四档优先级，维护成本较高，**推荐**在服务代码中分步查询或使用视图 + 函数封装。

---

## 9. 订单快照（强烈建议）

对账与客诉以 **下单时** 规则为准：在订单或 `order_refund_change_snapshot` 中保存 **`policy_id`、`policy_version`、`snapshot_json`**（可含当时命中的 `fee_mode`、`fee_value`、`fee_basis`）。

后台修改策略 **不追溯** 改历史订单解释。

## 11. 微信小程序（本仓库）接入要点

### 11.1 小程序 AppID（`channel_appid` 对齐）

- 工程配置：`project.config.json` → **`appid`**：`wx46e9e8119f9686a4`（与微信后台一致）。
- 票价 RPC `rpc_calc_ticket_price_tx` 入参 **`p_channel_appid`** 在 `miniprogram/utils/supabase.js` 中与上述 **同一 appid** 绑定，与 `price_app_channel` 渠道一致。
- **订单落库**时若存在 `appid` / `channel_appid` 字段，应写入该值，供退改签策略 §2.1 第 1、4 档匹配。

### 11.2 `order_channel`（粗粒度映射输入）

- 本小程序下单普遍使用 **`order_channel: 'miniprogram'`**（见 `play/play.js`、`order/order.js`、`imax/imax.js` 等与 `cinema_order_list` 交互处）。
- 映射到策略表粗粒度 **`channel`** 时，按 §4.2 / 服务端统一映射表转为 `wechat_mp` 等；**禁止**在小程序内手写多套映射，应与后端、票价文档一致。

### 11.3 前端是否实现规则引擎

- **否**。手续费、是否可退/可改，应以 **服务端**（或统一 RPC/Edge Function）返回为准；小程序仅展示结果与引导（门店改签、协议文案等）。
- 选座页 **退改签协议** 为 **告知与确认**：实现见 `miniprogram/pages/seat-select/seat-select.js` 中自定义弹窗（`scroll-view` 展示 `REFUND_AGREEMENT_MODAL_BODY`），**不改变**下单支付主流程，与 [影院退改签协议.md](./影院退改签协议.md) 产品口径一致。

### 11.4 建议的后端接口契约（预览/提交）

以下为 **建议**，以后端最终实现为准：

**预览（可选）**

```json
POST /api/refund-change/preview
{
  "order_id": "string",
  "policy_type": "refund | change",
  "tenant_id": "optional"
}
```

**响应（示例）**

```json
{
  "allowed": true,
  "policy_id": "uuid",
  "rule_id": "uuid",
  "fee_cents": 1000,
  "reason_code": null,
  "snapshot_hint": { }
}
```

小程序在「退票/改签」入口（若未来开放）仅传 **`order_id`** 与 **`policy_type`**，**不**在本地计算 `H` 与费率。

### 11.5 获取小程序 appid（运行时）

若需在运行时读取（例如写入日志或临时调试）：

```javascript
const accountInfo = wx.getAccountInfoSync();
const appid = accountInfo.miniProgram.appId;
```

上线业务字段仍以 **配置与订单落库** 为准，避免与 `project.config.json` 不一致。
