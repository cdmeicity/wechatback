# M6.2 购买限制改造：三步流程总结与实现要点

## 一、新三步流程（替代原 order_confirm 调用）

| 步骤 | 判断条件 | 不通过时 | 通过时 |
|------|----------|----------|--------|
| **第一步** | 比较 `app.globalData.cardinfo.balance` 与 `orderData.total` | 若 **balance &lt; total**：弹窗「您的余额不足，请到会员卡管理页面进行充值，或者解绑会员卡使用普通用户价格购票」→ 用户点确定 → **跳转会员卡管理页**（card-manage） | **balance ≥ total** → 执行第二步 |
| **第二步** | 判断 `app.globalData.cardinfo.cardStatus === 1` | 若 **cardStatus !== 1**：弹窗「会员卡状态异常，不能购票，可以到我的页面，问题反馈进行反馈」→ **取消购票流程，返回主页** | **cardStatus === 1** → 执行第三步 |
| **第三步** | 查表 `v_card_day_buy_number`：`card_number = cardinfo.cardNumber`，`buy_day = orderData.start_time 的日期`，取 `buy_num`；与 `cardinfo.maxBuyNum` 比较 | 若 **buy_num ≥ maxBuyNum**：弹窗「您已经达到了当日最大的购买数量，请明天再进行购买，或者解绑会员卡，用普通用户价格购买，感谢您的理解和支持！」→ 用户点确定 → **跳转主页** | **buy_num &lt; maxBuyNum** → **直接进入原有页面流程 M6.3**（不再做其他判断） |

**第三步通过后**：直接进入 **M6.3 会员时间判断** → M6.1 更新订单号 → M6.4 会员锁座 或 M6.5 会员卡支付，与改造前选座页的后续流程完全一致。

---

## 二、与原有逻辑的对比

- **原 M6.2**：一次请求后端 `order_confirm`，用返回的 `canBuy`、`balanceCheck`、`dayBuyInfo`、`showBuyInfo` 做 4 类判断。
- **新 M6.2**：
  - 第一步：前端用 **本地 cardinfo.balance** 与 **订单 orderData.total** 比较，不调后端。
  - 第二步：前端用 **本地 cardinfo.cardStatus** 判断是否等于 1。
  - 第三步：前端**查 Supabase 视图** `v_card_day_buy_number` 得到当日已购数量 `buy_num`，再与 **cardinfo.maxBuyNum** 比较。

原「当场购票限制」（showBuyInfo）在新流程里**未单独体现**，若业务仍需「本场次限购」，需在第三步之后或第三步中另行约定（例如视图中按场次维度统计，或后端再提供接口）。

## 三、实现前必须满足的依赖

### 3.1 app.globalData.cardinfo 需具备的字段

| 字段 | 当前是否已有 | 说明 |
|------|--------------|------|
| `balance` | ✅ 有 | 来自 `getUserMemberCard` 的 extra_data 或 `getCardDetail` 的 balance，选座前若从 card-manage/首页进，一般已拉过 card_detail，余额会更新。 |
| `cardStatus` | ❌ 当前无 | 需在**写 cardinfo 的地方**（如 app.js session 恢复、card-manage 绑定/刷新、index 刷新卡详情）从**卡详情接口或 Supabase** 取到并写入。若 dingxin `card_detail` 返回状态字段（如 `cardStatus`/`status`），在 `parseCardDetailResponse` 及合并进 cardinfo 时一并带上。 |
| `maxBuyNum` | ❌ 当前无 | 同上，需在卡详情或等级规则里拿到「当日最大购买数量」并写入 cardinfo。若来自 `get_card_level_rule` 的 `daily_ticket_limit`，需在绑定/刷新卡时解析并写入 `cardinfo.maxBuyNum`。 |

**结论**：第二步、第三步依赖 `cardStatus` 和 `maxBuyNum`，需要先**在卡详情/等级规则拉取与合并逻辑里**为 cardinfo 增加这两个字段，否则只能写死或跳过。

### 3.2 数据源与接口

- **第一步**：只读 `app.globalData.cardinfo.balance` 和当前页的 `orderData.total`（或 `total` 变量），无需新接口。注意两者**数值类型**统一（都转成 number 再比较），避免字符串比较。
- **第二步**：只读 `app.globalData.cardinfo.cardStatus`，需保证该字段有写入（见上）。
- **第三步**：
  - **Supabase**：需存在视图（或表）`v_card_day_buy_number`，且至少包含：
    - `card_number`（或 `cardNumber`）
    - `buy_day`（日期，格式与下面约定一致）
    - `buy_num`（当日已购数量）
  - **buy_day 的取值**：由 `orderData.start_time`（或 `showtime.startTime`）解析出**日期**，格式建议 `YYYY-MM-DD`（北京时区），与视图中 `buy_day` 类型/格式一致。
  - 若某卡当天无记录，查询结果为 0 条，则 `buy_num` 视为 **0**，0 &lt; maxBuyNum 即通过。

### 3.3 页面路径

- **会员卡管理（充值/解绑）**：`/pages/card-manage/card-manage`。若希望进入后默认在「已绑定卡」的 Tab，可保持现有逻辑；如需强调「充值」可加 query，例如 `?from=seat` 供 card-manage 做展示区分。
- **返回主页**：`wx.reLaunch({ url: '/pages/index/index' })` 或等价的「回到首页」。

## 四、边界与建议

1. **第一步「大于」**：业务上应理解为「余额足够支付」，即 **balance ≥ total** 才通过；若写成严格 `balance > total`，则余额刚好等于订单金额时无法支付。
2. **balance / total 类型**：比较前建议 `Number(cardinfo.balance)` 与 `Number(orderData.total)`（或当前计算好的 `total`），避免字符串 "100" 与 "50" 比较出错。
3. **cardinfo 为空或缺少字段**：若 `!cardinfo` 或 `cardinfo.balance == null`，建议第一步直接视为不通过并提示「会员卡信息异常，请到会员卡管理页查看」并跳转 card-manage；同理，若缺少 `cardStatus`/`maxBuyNum`，第二步/第三步需决定是「视为不通过」还是「暂时跳过该步」并打日志，建议与产品约定。
4. **第三步无记录**：查 `v_card_day_buy_number` 无行时，`buy_num` 按 0 处理，0 &lt; maxBuyNum 则通过。
5. **当日购票限制与「本场次」限制**：当前三步只做了「当日」维度（buy_num vs maxBuyNum），原 order_confirm 的「本场次购票限制」（showBuyInfo）未在新流程中体现；若业务需要，要么在第三步用同一视图增加场次维度，要么保留一次后端「本场次限制」查询。

## 五、替换方式小结

- **删除**：原 M6.2 中对 `cardApi.orderConfirm` 的调用以及基于其返回的 `canBuy`、`balanceCheck`、`dayBuyInfo`、`showBuyInfo` 的 4 段判断逻辑。
- **新增**：
  - 第一步：读 cardinfo.balance 与 orderData.total，不通过则弹窗并跳转 card-manage。
  - 第二步：读 cardinfo.cardStatus，不为 1 则弹窗并 reLaunch 到首页。
  - 第三步：请求 Supabase `v_card_day_buy_number`（card_number + buy_day），取 buy_num 与 cardinfo.maxBuyNum 比较，不通过则弹窗并 reLaunch 到首页。
- **保留**：第三步通过（buy_num &lt; maxBuyNum）后，**直接进入原有页面流程**，执行 **M6.3（会员时间判断）→ M6.1（订单号）→ M6.4/M6.5（锁座或会员卡支付）**，无需改动。

整体上，用「前端余额 + 本地卡状态 + Supabase 当日购买数」替代「后端 order_confirm 一次校验」，逻辑清晰；**唯一需要补齐的是 cardinfo 的 cardStatus、maxBuyNum 数据来源，以及 Supabase 视图 v_card_day_buy_number 的存在与字段约定**。若你确认这两点（或给出字段来源），我可以按该文档在 seat-select 里直接改 M6.2 的代码并补上 Supabase 查询方法。
